The problem

What is being built

A service that manages customer transactions through four operations — create one, fetch one, change one's status, and list a customer's transactions. The framework, database and build are provided; the work is the domain logic: deliberate validation, controlled state changes, and a clear response for every outcome including failure.

One input is missing. The exercise assigns each candidate a variant (currencies, maximum amount, transaction types, or one extra rule) in the invitation email. That variant was not available, so documented defaults are used and isolated to one place each — see Assumptions below.

Architecture

A thin web layer over a service that owns every rule

Each layer has one job. The controller speaks HTTP, the service decides what is allowed, the repository reads and writes. Request and response DTOs keep the HTTP contract independent of the persistence model.

Validation

State

How a transaction is allowed to change

Status is a small state machine. A transaction stays PENDING until it settles; from there it succeeds, fails, or is pulled before settling. Only a settled transaction can be reversed. Three states are terminal. A request to move to the current status is rejected — nothing would change.

API

Four operations

POST/api/transactions

Validate and store a new transaction. Body: transactionId, customerId, amount, currency, type. Returns the stored record at PENDING.

201 Created + Location  |  400 invalid  |  409 duplicate id
GET/api/transactions/{transactionId}

Fetch one transaction by id.

200 OK  |  404 not found
PATCH/api/transactions/{transactionId}/status

Change status. Body: { "status": "COMPLETED" }. Only allowed transitions succeed.

200 OK  |  404 not found  |  409 forbidden transition  |  400 unknown status
GET/api/transactions?customerId={customerId}

List a customer's transactions, oldest first. Empty array when the customer has none — not a 404.

200 OK  |  400 customerId missing

Assumptions

Decisions taken, and where to change them

Variant defaults

  • Currencies GBP, EUR, USD — application.yml
  • Maximum amount 10000.00 — application.yml
  • Types DEPOSIT, WITHDRAWAL, TRANSFER, REFUND — TransactionType enum

Design choices

  • Caller supplies the transaction id
  • New transactions always start PENDING
  • Same-status update is a 409, not a silent no-op
  • No auth, no paging, single node

Testing

32 tests, two levels

TransactionStatusTest — 17

Plain unit tests, no Spring. Allowed pairs, forbidden pairs, every self-transition, terminal states, initial state.

TransactionApiTest — 14

@SpringBootTest + MockMvc over real H2. The four cases the brief names, plus unsupported currency, over-limit amount, unknown type, both status outcomes, per-customer filtering, empty list, missing parameter.

The provided contextLoads sample test is kept. Each API test clears the table first, so nothing depends on order.

Seams

Known limitations & next steps

Limitations

  • No authentication or authorisation
  • No paging on the per-customer list
  • Duplicate detection is check-then-write; the DB unique constraint is the real guard
  • Assigned variant not yet applied

With more time

  • A @SupportedCurrency annotation so currency reports as a field error
  • Service unit test with a mocked repo and a fixed Clock
  • Idempotent create (same id + same body → existing resource)
  • A persisted status-change history
